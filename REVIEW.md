# Ревью API бронирования

Проверены методы `index`, `store`, `destroy` и `today` в `app/Http/Controllers/BookingController.php`, а также маршруты, модель `Booking` и миграция таблицы `bookings`.

> Этот документ фиксирует результаты ревью исходного состояния до выполнения части 2. Ошибки создания и отмены брони устранены в `StoreBookingRequest` и `BookingController`; `index` и `today` не менялись, как и разрешено заданием.

## Проблемы

### Critical — SQL-инъекция при создании брони

В `store` значения `room_id`, `starts_at` и `ends_at` подставляются в SQL-строку напрямую. До выполнения запроса эти поля не проверяются и не экранируются. Недоверенный ввод может изменить условие запроса; в зависимости от драйвера БД и формы запроса это создаёт риск SQL-инъекции.

**Исправление:** сначала валидировать входные данные, затем использовать Eloquent/query builder или параметризованные bindings. Не собирать SQL из значений запроса.

### Major — можно создать бронь от имени другого пользователя

`store` сохраняет `$request->all()`, а `user_id` входит в список разрешённых для массового заполнения атрибутов модели `Booking`. Поэтому клиент может передать чужой `user_id` и создать бронь, записанную на другого пользователя.

**Исправление:** брать автора только из `$request->user()->id`, не принимать `user_id` от клиента и сохранять только явно проверенные поля.

### Major — авторизация отмены отсутствует

`destroy` удаляет найденную бронь без проверки владельца. Любой аутентифицированный пользователь может отменить бронь, зная её идентификатор.

**Исправление:** разрешать удаление только автору брони; проверку выполнять через policy/gate или сравнение с текущим пользователем до удаления. Для отсутствующей брони сохранить ответ 404, для чужой — вернуть согласованный отказ в доступе.

### Major — конфликт занятости проверяется с неверными границами

Условие `starts_at <= new.ends_at AND ends_at >= new.starts_at` считает пересекающимися интервалы, которые только соприкасаются концами. Например, бронь 10:00–11:00 блокирует бронь 11:00–12:00, хотя встречи «впритык» разрешены.

**Исправление:** для полуоткрытых интервалов использовать условие пересечения `existing.starts_at < new.ends_at AND existing.ends_at > new.starts_at`.

### Major — проверка рабочего времени неверна для офисов и длительности

`store` проверяет только час начала, интерпретируя его в переданном смещении, а не в часовом поясе офиса комнаты. Время окончания не проверяется. Поэтому можно забронировать комнату до 09:00 или после 20:00 по местному времени офиса, а также провести встречу, пересекающую границу рабочего дня.

**Исправление:** загрузить офис выбранной комнаты, перевести оба времени из присланного ISO 8601 в часовой пояс этого офиса и проверить весь интервал на попадание в 09:00–20:00 местного времени.

### Major — правила длительности и шага времени не реализованы

Нет проверки, что начало раньше окончания, длительность составляет от 15 минут до 4 часов и оба времени кратны 15 минутам. Невалидные интервалы могут быть сохранены или привести к некорректному поведению проверки конфликтов.

**Исправление:** валидировать порядок времён, минимальную и максимальную длительность, а также шаг 15 минут. Возвращать понятные ошибки валидации с HTTP 422.

### Major — валидация выполняется после обращения к базе

Проверка конфликтов делается до валидации существования комнаты, формата дат и обязательных параметров. Пустые или некорректные данные могут дать ошибку БД/SQL вместо предсказуемого ответа API. Поля `room_id`, `title`, `starts_at` и `ends_at` не имеют явных правил валидации.

**Исправление:** до запросов к БД проверить обязательность, тип и формат полей, существование комнаты, а затем выполнить предметные проверки. Все ошибки пользовательского ввода возвращать в формате 422.

### Major — гонка между проверкой конфликта и созданием

Проверка занятости и `Booking::create()` выполняются отдельными операциями. Два параллельных запроса могут одновременно увидеть свободный слот и оба создать бронь. В текущей схеме нет ограничения БД, которое предотвращало бы пересечение.

**Исправление:** для PostgreSQL надёжный вариант — exclusion constraint по `room_id` и диапазону времени, с обработкой ошибки нарушения ограничения. Альтернатива — сериализовать создание для комнаты транзакцией и блокировкой строки комнаты, повторяя проверку внутри блокировки. Одной проверки в PHP недостаточно.

### Minor — `today` использует часовой пояс приложения, а не офиса

`whereDate('starts_at', today())` выбирает день по текущей дате приложения. Для комнаты в другом часовом поясе границы «сегодня» могут отличаться, поэтому список может быть неполным или включать брони соседней местной даты.

**Исправление:** вычислять начало и конец текущего дня в часовом поясе офиса комнаты, затем искать брони по временному диапазону.

### Minor — `today` может выполнять лишние запросы авторов

После выборки броней метод обращается к `$b->user->name` внутри `map`. Связь автора заранее не загружается, поэтому при нескольких бронях выполняется дополнительный запрос на каждого автора (N+1).

**Исправление:** загружать авторов вместе с бронями через `with('user')` (или выбирать нужные поля связи).

### Minor — ответы API не формируют явный ресурсный контракт

`index` возвращает сырые модели с пагинацией, `store` — модель напрямую, `today` — массив собственного формата. Поля ответа зависят от сериализации моделей и могут непреднамеренно меняться при добавлении атрибутов или связей.

**Исправление:** определить стабильный формат ответа и использовать API Resource либо явно формировать DTO/массив ответа. Это не мешает текущему функционалу само по себе, но усложняет поддержку клиентов API.

## Подозрительные места, которые сами по себе не являются ошибками

- **`index` ограничивает выборку текущим пользователем.** Это корректно для маршрута «мои брони» и соответствует ожиданиям приватности.
- **В `index` используется `paginate(20)`.** Это допустимо для списка; наличие пагинации предотвращает возврат всех записей сразу.
- **В `today` используется привязка `Room $room`.** Неявный route model binding — штатный механизм Laravel. Он вернёт 404, если комнаты с таким идентификатором нет.
- **Маршруты API закрыты `auth:sanctum`.** Аутентификация включена для всех четырёх операций. Она не заменяет проверку прав на конкретную бронь, поэтому проблему `destroy` это не устраняет.
- **Метод `index` сортирует через `orderByRaw('starts_at DESC')`.** В этой строке нет подстановки пользовательского ввода, поэтому это не SQL-инъекция. Для ясности можно заменить на `orderByDesc('starts_at')`.
- **Логирование создания после сохранения.** Такой порядок позволяет записывать идентификатор уже созданной брони. Однако `Log::withContext()` устанавливает контекст для последующих записей, а не только для следующего сообщения; если контекст должен быть локальным для одной записи, лучше использовать контекст канала/записи.

## Резюме

Перед эксплуатацией необходимо исправить SQL-инъекцию, привязку автора к текущему пользователю, проверку прав на отмену, валидацию и расчёт пересечений/рабочих часов по часовому поясу офиса. Для гарантии отсутствия двойной брони при параллельных запросах нужен механизм сериализации или ограничение PostgreSQL.
